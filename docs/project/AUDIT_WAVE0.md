## 1. Executive audit

**FACT — This is deployment path 1 of the blueprint's three: an Odoo-based ERP.** Not a custom platform and not an ERP-connected application. Evidence: four `__manifest__.py` files declaring `"version": "19.0.x.y.z"`; `.github/workflows/odoo-tests.yml` installing the addons into a real Odoo 19 database; models extending `account.payment`, `account.move`, `res.partner` and `sale.order` through `_inherit`. The blueprint's ADR-012 is therefore answered by evidence, not by assumption.

**FACT — Edition is Enterprise.** `c2p_property_lease` performs a registry check for `sale_subscription`, an Enterprise-only module, and deliberately keeps it out of `depends` because the licence forbids committing it and CI cannot install it.

**FACT — This is not a general ERP build. It is one industry vertical (`VRT-01`) on a mostly unbuilt platform.** The contracted scope is a property-management implementation for New Sinclair Property Management LLC, catalogued as 186 requirements (`BR-001`…`BR-186`) and 90 reports (`RPT-001`…`RPT-090`). Coverage, generated by `tools/check_requirement_matrix.py` rather than estimated:

| Status | Count |
| --- | --- |
| Built | 12 |
| Partial | 33 |
| Not started | 141 |

**This is the single most important finding, and it is a scope finding rather than a technical one.** The master directive's module list — manufacturing, POS, payroll, fleet, e-commerce — is roughly 80% outside this project's signed scope. The blueprint says so itself in §0: it "is not a claim that every listed feature belongs in every project", and §5 classifies most of that list `OPTIONAL`. Building toward the full registry would mean abandoning a contracted deliverable that is 24% started in order to begin a different, unsigned one.

**DESIGN — Adopt the pack as the engineering standard, applied to the contracted scope.** Its ten principles, eight quality gates, lifecycle, ADR discipline and documentation contract are all worth adopting as-is and are largely already honoured (§3). Its module registry should be adopted as a *fit-gap instrument* — the capability inventory in §2 — not as a build list.

**FACT — Engineering discipline is already close to the blueprint's standard, with specific exceptions.** Eight static checks run in CI; the addons install into a real Odoo 19 database in CI; 256 Odoo tests pass on `main`; the requirement matrix, data dictionary and status matrix are machine-checked against source so they cannot drift. The exceptions are in §4 and §6.

## 5. Process and cross-module gaps

The blueprint's §6 mandates end-to-end lineage. Mapping its canonical processes onto this vertical:

**Lease-to-cash (this project's L2C) — FACT, partially traceable:**

```
Unit (Draft→Available) → Lease (Draft→…→Active)  → PDC schedule (Expected)
   → cheque In Hand → Deposited → Cleared → account.move → GL
                              ↘ Bounced → Replaced
```

Built: unit release gate (BR-018), the twelve-state lease, the cheque gate (BR-075) and its approved-exception escape, seven instrument states, replacement chains, permanent bounce record.

**Breaks in the chain:**

1. **Cleared is asserted, not reconciled** (R1 below). The link from instrument to bank statement does not exist, so the last hop of L2C is a user's word.
2. **No arrears ageing.** The dossier reports cheque *shortfall* (contracted rent not covered by instruments), which is not the same as receivables ageing. BR-098 asks for arrears and the matrix now says so.
3. **Expected-cheque forward view partially duplicates payment terms.** Odoo already derives a due-date forecast from instalment payment terms. The *instrument* expectation is justified (a cheque is a physical object in custody); the *cash forecast* should read receivables or the two will drift. Recorded as a known correction.
4. **Intercompany (FIN-05) is absent** though BR-004 requires controlled reciprocal intercompany between the two entities.

**Record-to-report:** the Command Center reads domain models directly rather than a read model. Acceptable at this volume; the blueprint's §11 preference for validated read models becomes relevant at scale, not now.

## 6. Critical risks

Ordered by exposure. R1 and R2 are the ones I would fix before any new feature.

**R1 — Financial integrity: `cleared` bypasses native reconciliation. (High)**
BR-118 requires that no cheque is treated as cleared before bank or landlord confirmation. Today `action_pdc_clear` writes `pdc_state = 'cleared'` on a user's click, while Odoo's own `account.payment.state` and outstanding-account machinery sit unconnected beside it. By the blueprint's §17.2 this is an explicit *blocker* condition — "posting logic would bypass native accounting" — and by principle 4 (Financial Integrity) it is the most serious defect in the system. It is also **my own earlier design**, recorded as a correction in `docs/PROJECT_STATE.md`.
*Blocked on:* **OD-02** (custody control account) and **OD-05** (payment methods and custody controls). Cannot be fixed correctly without them, because the fix must know which account landlord-name cheques post to.

**R2 — Multi-company leak: two sensitive models have no record rule. (High, and fixable now)**
`c2p.head.lease` and `c2p.bank.facility` both declare `company_id` but neither appears in `security/c2p_security.xml`. Odoo does not create record rules implicitly, and the repository declares five explicitly for building, unit, lease, cheque exception and tenancy event — which establishes the convention and shows these two were missed. Under BR-004's two legal entities, a `group_property_user` can read **every head lease in the database** (ACL row 13 grants read) and a manager of either company can read **every banking facility**. Those are the two most commercially sensitive models in the system: landlord commitments and bank limits.
This is blueprint §17.2's "record rules leak company data" blocker and §10.1's access rules. **It is pre-existing on `main`, not introduced by recent work.**

**R3 — Twenty roles, two groups. (Medium, blocked)**
BRD §2.3 names twenty roles; the system has two. Every *(proposed)* role in `status_matrix.md` is a recommendation pending **OD-06**, and the approval matrix is what the blueprint's ADR-007 and principle 6 (segregation of duties) require. Six requirements are explicitly blocked on it. The mechanisms are built in the right place — the no-self-approval rule on the cheque exception is enforced on `write`, not in a button — but *who may approve what* is unanswerable today.

**R4 — Deploy gap: production is ten merged PRs behind. (Medium)**
Production was last upgraded 2026-10-06 to `c2p_property_lease 19.0.1.6.0`; `main` is at `19.0.1.12.0` and PR #25 takes it to `19.0.1.13.0`. The next deploy installs everything at once, including two modules of UI that have never run outside CI. **Two migrations have never executed anywhere** (`19.0.1.8.0`, `19.0.1.12.0`), because CI builds fresh databases and no migration runs there.

**R5 — The local gate cannot catch Odoo-runtime faults. (Medium, structural)**
There is no Odoo in the dev container, so none of the eight local checks loads a view, instantiates a model or runs against the ORM. In PR #14 the full local gate passed on two commits CI then rejected — once for `ir.ui.view.groups_id`, which v19 removed and which fails the whole install. One static guard was added for that class of error; the gap is permanent and must be stated in every report. **Never run on an Odoo.sh staging branch** — only CI and production, which makes CI the sole pre-production gate.

**R6 — VAT documented, not enforced. (Medium)** ADR-006 localization gap.

**R7 — Reports: 90 catalogued, 0 Built. (Medium)** 22 Partial, 68 Not started. The BI layer is thinner than the dashboards suggest.

## 9. One thing I did not do, and why

The pack's `README.md` installation step 2 says to place its `CLAUDE.md` at the repository root and copy its `docs/` into the repository. **I did neither, on two grounds:**

1. **This repository is public** (`CLAUDE.md` hard rule 1) and the pack describes itself as "A C2P Group reusable, vendor-aware ERP software delivery standard" — commercial methodology IP. Committing it publishes that standard, and its templates, to anyone. That is the sponsor's call to make knowingly, not a side effect of an install step. **D8.**
2. **The existing root `CLAUDE.md` is project-specific and hard-won.** It records six distinct defects this codebase has produced, the v19 API differences that have actually broken installs, and the two lessons about building refusals. The pack's version is a generic standard. Overwriting would destroy knowledge that has already cost CI runs and one production outage to acquire.

**DESIGN — the merge instead:** keep the project file as the always-on contract, add a short section pointing at the blueprint as the governing standard, and adopt the pack's mandatory response format for development reports. That satisfies the pack's intent (§20: "keep `CLAUDE.md` concise; move bulky specifications into versioned docs") without losing either document. Pending D8, the blueprint is referenced by section number and not vendored.

## 10. Next smallest safe development task

**R2 — add the two missing multi-company record rules.**

Chosen because it is the only High risk that is **not** blocked on a sponsor decision, it is small and self-contained, it is a security fix rather than a feature, and it closes a blueprint §17.2 blocker condition.

**Scope:** two `ir.rule` records in `c2p_property_lease/security/c2p_security.xml` for `c2p.head.lease` and `c2p.bank.facility`, `domain_force` `[('company_id','in',company_ids)]`, matching the five that exist. Plus tests proving a user of company A cannot read company B's head leases or facilities — and, because the blueprint demands negative tests, that the existing five rules still hold. Manifest version bump (hard rule 3: without it Odoo.sh will not apply the change to a database).

**Acceptance (GIVEN/WHEN/THEN):**

- GIVEN two companies each with a head lease, WHEN a `group_property_user` of company A searches `c2p.head.lease`, THEN only company A's record is returned.
- GIVEN the same, WHEN a `group_property_manager` of company A reads company B's facility by id, THEN access is refused.
- GIVEN a user with both companies active, WHEN they search either model, THEN both companies' records are returned.
- GIVEN the change, WHEN the existing suite runs, THEN no previously passing test fails.

**Evidence required before claiming done:** CI green on the Odoo job, those tests executed and named in the report. Not the local gate, which cannot see record rules at all.
